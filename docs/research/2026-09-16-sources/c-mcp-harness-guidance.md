# 2026 State of the Art: MCP Tool-Surface Design & Agent-Harness Construction
### vs. CodeLens MCP (`/Users/bagjaeseog/codelens-mcp-plugin`)

Compiled 2026-09-16. All local facts verified against the live repo (`tools.toml`, `presets.rs`, `protocol.rs`, ADRs). All external facts verified by opening the cited page (WebFetch) unless marked UNVERIFIED (WebSearch summary only).

---

## 1. Executive summary

CodeLens's own architecture decisions (ADR-0015 host-neutral contract, ADR-0016 default-surface ≤20, ADR-0010 telemetry diet) are **directionally correct and ahead of most MCP servers** — they anticipate exactly the problems Anthropic and the MCP steering group are now documenting in 2026: tool-count-driven accuracy collapse, model-name-based routing brittleness, and the need for host-declared capabilities instead of server-side executor bias.

The gap is **narrower than a first read of the preset tables suggests, and one layer more specific**:

- ADR-0016's ≤20-tool default surface **is implemented and CI-gated** — verified directly in `crates/codelens-mcp/src/integration_tests/protocol_tools_list.rs`: the bare, parameterless `tools/list` call against `ToolPreset::Full` asserts `names.len() <= 20`, and a separate test asserts `REVIEWER_GRAPH_TOOLS.len() <= 20` by name, citing ADR-0016 in the comment. This is *not* a gap; an earlier pass of this review incorrectly read `PLANNER_READONLY_TOOLS` (41) and `BUILDER_MINIMAL_TOOLS` (47) as violations of that cap. They are not — the same test file's comments describe them as deliberately wider, named presets ("the full emitter+target set") that a session must explicitly select via `set_profile`, not defaults.
- The real, narrower finding: `docs/host-adaptive-harness.md` names `readonly` as Claude Code's **default profile** and `builder` as Codex/Cline/Windsurf's **default profile** — and those profile names resolve (`presets.rs:58-59`) to `PlannerReadonly` (41 tools) and `BuilderMinimal` (47 tools), not to the CORE-20/`ReviewerGraph` surface. So the harness's own documented steady state for those hosts is a 41–47-tool surface, which does sit inside/above the exact band Claude Code's own tool-search docs call out ("accuracy degrades with more than 30-50 tools") and inside/above Cursor's community-reported 40-tool cap. Whether a *fresh, unparameterized* `tools/list` call against a session that starts life already scoped to one of these presets (e.g., via the repo's separate readonly/mutation launchd daemons) returns 20 or the full preset count is **not resolved by any test found in this pass** — the one CI test that proves the ≤20 cap initializes `AppState` with `ToolPreset::Full`, not `ToolPreset::PlannerReadonly`. This is a concrete, bounded question for the local surface-instrumentation track, not a documentation-only fix (see §4).
- `ToolAnnotations` injects non-spec fields (`approvalRequired`, `auditCategory`, `toolNamespace`, `tier`) as top-level keys alongside the four spec-defined hints, rather than under `_meta` — the documented MCP extension point — creating forward-compat risk against the four live SEPs (1913, 1862, 1984, 2417) reshaping this exact object. This one **is** a verified, real gap (§3, Gap #1 below).
- The 2026-07-28 MCP spec added `ttlMs`/`cacheScope` to `tools/list` responses specifically to improve prompt-cache hit rates for large tool lists; CodeLens has zero references to either field (grep-verified).
- CodeLens's polymorphic verb-facade pattern (`search(mode=…)`, `graph(mode=…)`, `review(mode=…)`) is independently validated by Anthropic's own tool-design guidance ("consolidate frequently-chained multi-step tasks into one tool" — their canonical example is collapsing `list_users`/`list_events`/`create_event` into one `schedule_event`). This is a strength, not a gap, and should be stated as such rather than re-litigated.
- CodeLens does **not** implement MCP's Roots, Sampling, or Logging capabilities (grep-verified: no `roots/list`, `sampling/createMessage`, or `logging/setLevel` handlers in `src/`; `surface_manifest.rs` already declares `"sampling": false`). The 2026-07-28 spec's 12-month deprecation of exactly these three features therefore has **zero migration cost** for CodeLens — a fully resolved item, not an open question.

Net: the highest-confidence, lowest-effort fix is the annotation-schema hygiene issue (`_meta` placement), not a tool-count "fix" — the tool-count story is a genuine design tension between the ADR's small safe default and the harness's own documented default profile per host, and needs one bounded runtime check (which preset a freshly-connected session's first `tools/list` actually returns) before any code changes, not a redesign.

## 4. Open questions / conflicting signals

- **Cursor's 40-tool cap has no confirmed official-docs citation** in this pass (only Cursor's own community forum, across at least 6 independent threads, plus one third-party aggregator site — no `docs.cursor.com` page found). Treat as Medium confidence: the number is unusually consistent across independent forum reports and Cursor staff replies in those threads, but one forum thread mentions an unconfirmed possible increase to 80 "earlier in 2026" that no official doc corroborates. Do not treat as spec-grade without an official citation.
- **Practitioner token-cost numbers (scottspence.com, getunblocked.com) are single-setup/aggregated-secondary measurements**, not controlled experiments; they're useful for order-of-magnitude reasoning ("dozens of tools ≈ tens of thousands of tokens") but shouldn't be quoted as CodeLens-specific predictions without re-measuring CodeLens's actual `tools/list` payload size per profile.
- **Verb-facade discoverability under Tool Search (Gap #6) is a genuine open empirical question**, not resolved by any source read in this pass — it needs a CodeLens-specific eval, not more literature review.
- **Whether ADR-0016 §5's host-capability-gated deferral is actually implemented at runtime** could not be confirmed from static file reads alone (this task was scoped read-only); this is a "verify, don't assume" item for whoever picks up Gap #1/#5.
- **MCP roadmap explicitly deprioritizes both tool annotations and a registry** relative to "agentic messaging" and "progressive discovery" — this is a mild tension with Gap #2 (annotation-schema hygiene): fixing the annotation `_meta` placement is still worth doing for robustness, but it is not where the protocol's own steering group is currently investing, so expect slower external convergence than the SEP list alone would suggest.
